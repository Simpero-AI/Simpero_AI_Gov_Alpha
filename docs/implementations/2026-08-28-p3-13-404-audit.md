## What this is

An audit, not a build: every public-route handler's failure path — bad
token, unknown link, expired, revoked, already-submitted, wrong email —
must return the exact same 404 body, so the public surface can never be
used as an oracle to distinguish these cases from each other.

## Audit method

Read every public route handler (`app/api/public_intake.py`,
`app/api/public_uploads.py`) and the two shared dependencies
(`app/core/public_dependencies.py::get_public_link_db`/
`get_public_session_db`) end to end, then traced the actual RLS keyhole
policies (`alembic/versions/b4f8e1c3a962_intake_keyhole_policies.py`) that
back every one of those handlers' failure paths, rather than trusting the
code comments' own claims about what the database does. Then wrote a new
consolidated test file empirically proving the finding, since no existing
test asserted byte-identical *bodies* (as opposed to status codes) across
the whole surface at once.

## Finding: the contract already held everywhere it needs to

Every session-authenticated route (`GET /questions`, `POST /answers`,
`POST /submit`, `POST /uploads/presigned-url`, `POST /uploads/{id}/complete`)
funnels its link-identity/session-validity failures through the same two
dependencies, both of which raise `HTTPException(404, "Not found")` on
every failure path with no exceptions:
- A malformed/garbage/wrong-secret session token → caught by
  `decode_intake_session_jwt`'s `AuthenticationError`, mapped to 404 in
  `get_public_session_db` itself, and again independently in two
  duplicated `_decode_claims` helpers (`public_intake.py`,
  `public_uploads.py`) for the two routes that need `claims.email` beyond
  what the dependency yields.
- A session token naming a `link_id` that was never a real row →
  `IntakeLinkRepo.get_by_id` returns `None` → 404.
- A revoked link → invisible via `intake_session_lookup`'s `USING` clause
  (`status IN ('pending', 'submitted')` — 'revoked' isn't admitted) → the
  `get_by_id` lookup above returns `None` under RLS → 404.
- An expired link → `intake_session_lookup` also checks
  `expires_at > now()` unconditionally, regardless of the stored `status`
  column — a still-`pending`-but-past-expiry row is invisible the same
  way, closing the gap where a lazy-expire write hasn't run yet → 404.
- A non-`pending` link at a deeper write-time check (`/answers`'
  `update_draft_answers`, `/submit`'s `get_pending_by_id_for_update`) →
  each of those RLS-backed writes/locked-reads independently returns
  `None`/zero-rows for the same underlying reason → 404, same body.

All of these produce the literal same JSON body,
`{"detail":"Not found"}`, confirmed byte-for-byte (not just same status
code) by the new test suite below.

## One thing NOT part of this contract, deliberately, documented so it
isn't mistaken for a gap later

`POST /uploads/{id}/complete` has a **second, distinct** 404:
`head_object(storage_key)` returning falsy (`"Uploaded object not found
-- the presigned PUT may not have completed"`). This is a real 404 with a
*different* body than the uniform one. **This is correct, not a
violation** — reasoned through explicitly, not just left alone:
- This code path is only reachable *after* `get_public_session_db` has
  already succeeded — i.e., the caller already holds a verified session
  for a real, live link. The 404-only contract exists to stop someone
  *without* a valid session/token from learning anything about link
  existence/status; it says nothing about distinguishing business-logic
  outcomes for someone who already has proven access.
- The `storage_key` this checks is deterministically derived from the
  caller's *own* `link.deal_id`/`clerk_org_id` — a valid session holder
  can't use this to probe any other org's or link's objects, only their
  own upload attempts.
- Same reasoning covers `/presigned-url`'s distinct 409 bodies (dedupe
  conflict, file-count ceiling) — precondition failures for an
  already-authenticated caller, not link-identity oracles, and 422s
  across the whole surface (payload validation) are in the same category.

The ticket's own text scopes the audit to `public_intake.py` literally;
the broader "every public route" language in the P3 brief's section 2.2 is
about the link-identity/session-validity failure family specifically —
confirmed by re-reading that section's own examples ("bad token, expired,
revoked, already submitted, wrong email"), all of which are pre-
authentication states, not post-authentication business outcomes.

## What was built

- `tests/test_public_404_contract.py` (new, 21 tests) — the empirical
  proof the audit above wasn't just a code-reading exercise:
  - `_SESSION_ROUTES`: every session-authenticated route in one list, so a
    future new public route is easy to add here and easy to notice if
    it's forgotten.
  - Parametrized across all 5 routes x 4 failure modes (garbage token,
    unknown link_id, expired link, revoked link) = 20 tests, each
    asserting both `status_code == 404` and `content ==
    b'{"detail":"Not found"}'` — the byte-identical body, not just the
    status code every individual route's own test file already checked.
  - One combined test
    (`test_all_failure_bodies_across_the_whole_surface_are_byte_identical`)
    collecting all 20 response bodies into one list and asserting mutual
    identity directly, the strongest single assertion of the contract —
    mirrors `tests/test_public_intake_session.py`'s existing
    `test_byte_identical_404_across_every_failure_mode` (which already
    covered `POST /session` alone) extended to the whole surface.
  - A local `link_factory` fixture, deliberately duplicated from
    `test_public_intake_session.py`'s own (not moved to `conftest.py`),
    matching this repo's established precedent for small test-local
    fixtures — this file's version doesn't need a `questions_snapshot`
    the way the answers/submit routes' own dedicated test files do, since
    every case here fails before any snapshot is ever read.

## A real bug this test file's own construction surfaced (test
infrastructure, not a product bug)

The combined test makes 20 requests in one test function against
`httpx.ASGITransport`'s single synthetic client address — hit P3-12's
5-request/10-second IP throttle mid-test (one request got a genuine `429`
instead of `404`, which would have been a false "byte-identical" failure
unrelated to what this test exists to check). Fixed by clearing
`ratelimit:*` Valkey keys between every request in that one test, mirroring
the pattern `test_public_intake_session.py`'s own lockout test already
uses for the same reason.

## Deviations / judgment calls worth flagging

- **Scope interpretation**: the `/complete` and `/presigned-url` distinct
  4xx bodies (documented above) were judged out of the 404-only contract's
  actual security scope rather than "fixed" to match the uniform body —
  flagging in case a stricter reading (byte-identical across *every* 4xx
  on the whole surface, not just the link-identity family) is actually
  wanted; that would be a larger, different piece of work than what this
  ticket's own text and section 2.2 describe.
- This ticket needed no code changes to `app/api/` or `app/core/` at all
  — the contract was already correctly implemented by P3-07/08/09/10/11's
  own careful adherence to the pattern P3-07 established first. This
  ticket's entire value is the empirical proof + the documented reasoning
  for the one deliberate exception, not a bug fix.
