`get_public_session_db`. The explicit finish: writes the

## Two design decisions this ticket needed before implementation (architect
pass, both approved by Vansh before build)

1. **Document-count gate scope**: the ticket text says "≥1 verified-or-
   pending `data_source` for the deal" — read literally, `deal_id`-scoped.
   Built `intake_link_id`-scoped instead (new
   `DataSourceRepo.count_for_intake_link_by_status`), same reasoning P3-10
   already established: a `deal_id`-scoped count would let an org-side
   authenticated upload (`/api/uploads/*`, never blocked while a link is
   pending) satisfy an external recipient's own upload requirement with
   zero uploads of their own. Same spec-gap family as P3-10's own
   deviation — flagged, not silently resolved. Status filter: literal
   `status IN ('pending', 'verified')` — traced the ingest job
   (`app/jobs/tasks/`) and confirmed `ocr_needed` is unreachable by
   anything in this repo today, so "verified-or-pending" and "not
   known-bad" are currently identical; went with the literal reading.
2. **Submit sequencing/locking**, the one genuinely non-mechanical design
   call: `intake_response_insert`'s `WITH CHECK` (`b4f8e1c3a962`) requires
   the link to still be `status = 'pending'` **at INSERT time** — so the
   response row must be written *before* the status flips to `submitted`.
   But that ordering alone reopens the exact race the ticket's own AC
   warns about ("fails closed... rather than duplicating the response
   row"): two concurrent `/submit` calls could both read `pending` before
   either writes, both pass validation, both insert a response row. Fixed
   with a `SELECT ... FOR UPDATE` row lock on the link
   (`IntakeLinkRepo.get_pending_by_id_for_update`, same idiom as
   `get_pending_for_deal`'s reissue-race lock) taken as the very first
   step — a second concurrent call blocks on the lock until the first
   commits, then sees `submitted` and cleanly 404s.

## What was built

- `app/repo/DataSourceRepo.py` — `count_for_intake_link_by_status(link_id,
  statuses=("pending","verified"))`.
- `app/repo/IntakeLinkRepo.py` — `get_pending_by_id_for_update(link_id)`
  (`FOR UPDATE`, `None` if not found or not `pending`).
- `app/schemas/public_intake.py` — `IntakeSubmitResponse` (`submitted:
  bool`, `submitted_at: datetime`, wire key `submittedAt`).
- `app/api/public_intake.py` — `_decode_claims` (duplicated from
  `public_uploads.py`, matching this file's existing precedent of
  duplicating small router-local helpers) + `POST /submit`. Exact sequence:
  locked reload (404 if not `pending`) → completeness gate (422) →
  document gate (409) → insert `DealIntakeResponse` + explicit `flush()`
  (load-bearing, see below) → mutate `link.status`/`submitted_at` in place
  → audit row → `flush()` + `refresh(link, ["submitted_at"])` → response.
- `app/models/deal_intake_response.py` — **a necessary bug fix, not a
  design change**: `implicit_returning: False` + client-side
  `default=uuid.uuid4` on `id`, exactly mirroring `HumanAuditLog`'s
  existing fix (documented in this status doc's P3-07 Flagged entry).
  `dd_public` has INSERT-only (no SELECT) on `deal_intake_response`
  (deliberate, per that table's own migration docstring) — Postgres
  requires SELECT to satisfy a RETURNING clause, and this table had never
  actually been written to before P3-11, so the gap was latent until now.
- `tests/test_public_submit_api.py` (new, 8 tests): happy path (response
  row + status flip + exactly one audit row), missing-required-answer 422,
  zero-documents 409, document gate correctly ignoring another link's
  uploads and the org's own authenticated-path uploads (the scoping
  decision, tested explicitly, not just trusted), double-submit — second
  call 404s **and** exactly one response row exists after both calls (not
  just the status code), IP/user-agent persisted on both the response and
  audit rows, the `"unknown"`→`None` IP mapping tested in isolation,
  cross-org isolation.

## Two things discovered empirically during implementation, not just
style choices

- **The `db.add(response)`-then-`link.status = ...` ordering in Python
  does NOT guarantee INSERT-before-UPDATE at the SQL level.**
  SQLAlchemy's unit-of-work doesn't preserve code-call order across
  unrelated ORM objects — without an explicit `await db.flush()` right
  after `db.add(response)`, the status UPDATE could flush first, flipping
  the link to `submitted` before the response INSERT runs, which
  `intake_response_insert`'s `WITH CHECK` then rejects (an RLS violation,
  not a clean error). The explicit flush forces the ordering the policy
  requires.
- **`func.now()` assigned to an ORM attribute for an UPDATE doesn't
  auto-populate in memory the way it does for an INSERT.** `AsyncSession`
  doesn't emit a `RETURNING` for a plain attribute-mutation UPDATE, so
  reading `link.submitted_at` right after the flush would trigger an
  implicit lazy-load outside the async greenlet (`MissingGreenlet`).
  Fixed with an explicit `await db.refresh(link,
  attribute_names=["submitted_at"])` before building the response.

based on P3-08's commit; `p3-10-public-uploads`, based on `origin/staging`
directly) that share no common ancestor beyond `origin/staging` itself —
neither is an ancestor of the other. GitHub PRs support only one base
branch, so whichever is picked, the diff will include the *other*
branch's commits too (already under separate review in PRs #151/#150/
#153). Opened against `p3-10-public-uploads` as base; the PR description
explicitly calls out which commits are actually new to this PR (the
Alembic merge migration + this ticket's own implementation commit) so a
reviewer isn't confused into re-reviewing P3-09/P3-10's already-covered
work.

## Deviations / judgment calls worth flagging

- **Response shape**: `{submitted: true, submittedAt: <ISO datetime>}` —
  a minimal ack echoing the real persisted `submitted_at` (via the
  refresh, not a client-side timestamp). Not explicit in the ticket text.
- **Audit payload**: `{"link_id": str(link.id), "document_count":
  doc_count}` — extended past the bare `{"link_id": ...}` shape other
  routes in this file use, since the document count was already in hand
  and seemed like a reasonable addition to the audit trail for a submit
  event. Flagging in case a stricter minimal shape matching the other
  call sites exactly is preferred instead.
